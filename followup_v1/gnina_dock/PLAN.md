# 실험 C — gnina로 탐색까지 (사전 등록, 2026-10-29 10:10)

**gnina 탐색 pose가 하나도 존재하지 않는 시점에 작성한다.** 비용 측정(job 439369)은 시간만 재고 pose를 버린다.
`followup_v1/PLAN.md`를 상속하며, 아래 항목만 다르다.

## 왜 하나

실험 B(재채점)에서 gnina가 apo multi − single = +0.529 Å, CI [+0.107, +1.046]을 보였다.
그런데 그 pose는 **Vina가 만든 것**이다. gnina는 Vina가 준 것 중에서만 골랐다.

사용자 지적: 도킹은 Vina로, 점수는 gnina로 하는 것이 문제 아닌가.
답: 쌍 비교는 타당하다(생성이 양쪽 arm에 동일하므로). 그러나 **sampling–scoring mismatch**가 남아
주장할 수 있는 범위가 "Vina pose를 gnina로 재채점했을 때"로 좁아진다.

이 실험은 **생성과 선택을 같은 함수로** 통일해 그 제약을 없앤다.

| 실험 | 생성 | 선택 | 무엇을 말할 수 있나 |
|---|---|---|---|
| A (budget50) | Vina | Vina | 확증 검정. Vina 파이프라인에서의 효과 |
| B (rescore) | Vina | Vinardo / gnina | 선택만 바꿨을 때. mismatch 있음 |
| **C (이 실험)** | **gnina** | **gnina** | **mismatch 없는 조건에서의 효과** |

## 설계

`expand_v1`의 입력을 **그대로** 재사용한다. 수용체 PDBQT, 리간드, box 전부 동일하므로 A·B와 직접 비교된다.
재준비하지 않는다.

- arm 4개 동일: holo/apo backbone × single/multiple sidechain 상태.
- **예산 맞춤 유지**: arm마다 호출 수 동일. single은 수용체 1개에 seed N개, multi는 수용체 n개에 N회를
  round-robin. n = 1이면 single과 정확히 같아진다. **multi가 더 많이 탐색해서 이기는 일은 불가능하다.**
- `--seed 20261028 + k`, `--num_modes 9`. box는 해당 backbone의 기준 리간드에서 나온 것(A·B와 동일).
- **호출 수 N과 exhaustiveness는 비용 측정 결과를 보고 정한다.** 정하는 기준은 아래에 미리 적는다.

### 호출 수를 정하는 규칙 (결과를 보기 전에 고정)

비용 측정은 **pose를 버리고 시간만** 재므로, 이 선택은 도킹 결과와 무관하다.

1. exhaustiveness는 **32**로 둔다(A·B와 같은 값). 비용이 감당 불가일 때만 8로 내리고, 그 사실을 적는다.
2. 호출 수 N은 **8 이상**에서 전체 비용이 **GPU 24시간 이내**가 되는 가장 큰 값으로 하되, 50을 넘지 않는다.
3. N을 정한 뒤에는 바꾸지 않는다. 결과를 보고 N을 늘려 재시도하지 않는다.
4. N < 50이면 A의 50호출 결과와 **예산이 다르므로** oracle·top-5·성공률을 직접 비교하지 않는다.
   비교는 **같은 run 안의 arm 간**에서만 한다.

## 지표와 판정

A와 **같은 지표를 같은 방식으로** 쓴다. 사례별 쌍 비교(single RMSD − multi RMSD, 양수면 multi가 좋음),
상동성 component 단위 cluster bootstrap, symmetry-aware in-place RMSD, 성공 ≤ 2 Å.

- 주 대비: **apo multi − single**, top-1과 **중복 제거 top-5**(1 Å 간격) 둘 다.
- **이 실험은 확증이 아니다.** `followup_v1/PLAN.md` §다중검정에 따라 확증 검정은 A의 P1/P2 둘뿐이다.
  C는 **사전 등록된 탐색 실험**이며, 양성이어도 "확증됐다"고 쓰지 않는다.
  C의 역할은 **B의 mismatch 교란을 제거하는 것**이고, 그 목적에 한해서만 해석한다.

## 결과와 무관하게 함께 보고할 것

- **gnina 학습 자료 누출**은 B와 똑같이 남는다. 오히려 **탐색까지 gnina가 하므로 더 크게 작용할 수 있다**:
  학습 자료에 있는 복합체라면 CNN이 정답 pose 쪽으로 탐색을 유도할 수 있다.
  따라서 **절대 성공률은 B보다도 더 낙관적으로 편향**됐다고 가정하고, 절대 성능을 주장하지 않는다.
  주 대비는 같은 사례 안에서 arm만 다른 쌍 비교이므로 누출이 양쪽에 동일하게 들어가 차이는 편향되지 않는다.
- **gnina v1.1**을 쓴다. 최신 v1.3.x는 glibc 2.35를 요구하고 이 클러스터는 2.34다(컨테이너 필요).
  v1.1은 2023-12 빌드이므로 최신 CNN 가중치·버그 수정이 빠져 있다. 버전을 기록한다.
- A·B와 **pose 집합이 다르다.** C의 oracle은 gnina 탐색의 생성 능력이고, A·B의 oracle은 Vina의 것이다.
  둘을 "어느 탐색이 더 좋은가"로 비교하는 것은 **별도 기술 통계**로 분리해 보고하며, 주 질문이 아니다.
- 비용 측정에서 쓴 pose는 전부 버린다(`probe/`). 본 실행은 새 디렉터리에 쓴다.
